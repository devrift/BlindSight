Core Philosophy: Fail Loudly, Never Optimistically #

Blind and low-vision pedestrians face life-threatening hazards from overhead tree branches, low wires, drop-offs, and quiet electric vehicles. Traditional electronic aids cost thousands of dollars, while smartphone apps frequently freeze silently or hallucinate descriptions.

The Core Tenet: A mobility aid must fail loudly, never optimistically. Every tier reports its exact live condition. No endpoint ever synthesizes placeholder data, serves a cached expired JPEG, or pretends an offline service is healthy. A missing neural model, dead sensor, or lost network generates an immediate, honest spoken alert.

Three Golden Engineering Constraints:

  • Zero-cloud collision reflex: If cloud servers go down or cellular signal drops, the ultrasonic stop and steer reflex must function with 100% autonomy on raw hardware.
  • No silent failures: If an ESP32-CAM frame drops or an audio buffer underflows, the watchdog trips and announces the failure state.
  • Accessible by design: WCAG AAA compliant palette (#05070c background, #f59e0b high-visibility amber), touch targets ≥56px (primary mic button 112px), single assertive screen-reader live region.

Quickstart Guide #

Deploy the BlindSight companion gateway in three simple steps. You do not need to be a developer to get running on Windows, Linux, or a Raspberry Pi.

Download the latest release zip from GitHub, unpack it anywhere (e.g., C:\BlindSight), and double-click the automated starter script:

git clone https://github.com/devrift/blindsight.git
cd blindsight
start_blindsight.bat

The first run automatically installs dependencies and opens http://localhost:5000 in your default browser.

On Raspberry Pi OS (Bookworm or Bullseye) or any Debian-based Linux distribution:

git clone https://github.com/devrift/blindsight.git
cd blindsight
chmod +x start_blindsight.sh
./start_blindsight.sh

The script displays both the local IP address and the HTTPS certificate address for pairing mobile phones on the same Wi-Fi network.

To run the Flask and edge-vision server in an isolated virtual environment:

python3 -m venv .venv
source .venv/bin/activate    # On Windows: .venv\Scripts\activate
pip install -r edge_server/requirements.txt
python3 edge_server/server.py

Pairing Your Smartphone

Connect your mobile device to the same Wi-Fi network as the gateway machine:

  • Android Phone (Chrome / Edge / Native Shell): Open the https://<gateway-ip>:5000 URL printed in the terminal. Accept the self-signed certificate once, permit microphone access, and speak "hey BlindSight".
  • iPhone / iPad (Safari): Apple restricts web apps from continuous wake-word background listening. BlindSight automatically detects iOS and activates dictation mode: tap the large button, tap the microphone icon on the native iOS keyboard, dictate, and tap Ask. Speech audio replies back through the neural voice engine.
  • Local Workstation: Simply browse to http://localhost:5000.
Optional Cloud Intelligence: To enable generative vision questions beyond the local ONNX model, copy edge_server/.env.example to edge_server/.env and supply your OPENROUTER_API_KEY=sk-or-.... Without a key, offline reflex, memory, and status remain 100% active.

Three-Tier Safety Architecture #

BlindSight decouples immediate life-safety reflexes from computationally intensive edge computer vision and high-level conversational AI.

Tier 0: Ultrasonic Reflex

Runs directly on the ESP32 DevKit V1 microcontroller. Reads 3 ultrasonic sensors simultaneously. If any centre obstacle is detected within 25 cm, it interrupts all routines and streams stop.wav over I2S to the PCM5102 DAC in under 10 ms.

Hardware: ESP32 • 3x HC-SR04 • PCM5102 DAC

Tier 1: Edge Machine Vision

Hosted on a Raspberry Pi 3B+ or local gateway laptop. Executes a YOLOv8-nano ONNX neural network in an isolated subprocess (~1.5 s inference per frame). Operates completely offline, converting bounding boxes into clear spatial announcements.

Runtime: ONNX Runtime • edge-tts • espeak-ng

Tier 2: Cloud Companion

Voice-first progressive web app paired with native Android shell. Provides hands-free wake word detection, long-term personal memory (up to 20 facts saved locally), 7 spoken languages, and rich scene Q&A via OpenRouter vision-language models.

Stack: TypeScript PWA • Web Audio • Android Shell

Hardware & Wiring V2 #

The production wiring specification eliminates fragile dual-rail Arduino distribution boards in favor of a unified 5V 3A DC buck converter with a single common ground plane.

Critical Divider Rule: The ESP32 GPIO pins are strictly 3.3V tolerant. HC-SR04 ECHO pins output 5V logic pulses. Never connect an ECHO pin directly to an ESP32. Every ECHO wire requires a voltage divider: ECHO → 1 kΩ → GPIO → 2 kΩ → GND.

Unified 5V 3A Buck Architecture

  • Power Source: 12V Li-ion battery pack or 12V 2A DC wall adapter.
  • Protection: 3A fast-blow inline fuse on the 12V positive rail.
  • Step-Down: High-efficiency LM2596 or XL4015 buck regulator calibrated to 5.05V DC under load.
  • Common Ground: All sensor grounds, DAC ground, ESP32 grounds, and buck GND bonded together at a single bus bar to eliminate ground loop hum in audio.

ESP32-CAM AI Thinker Configuration

The camera module sits in a lightweight headmount/chestmount frame, capturing 320x240 JPEG frames and streaming them wirelessly to the main ESP32 over connectionless ESP-NOW.

  • Power: 5V Rail & Common GND. Place a 470–1000 µF, ≥6.3V electrolytic capacitor directly between the camera 5V and GND pins to suppress WiFi burst voltage drops.
  • Flashing Mode: Ground GPIO 0 during power-up or reset to enter download mode. Disconnect GPIO 0 for standard boot.
  • Serial Uplink: U0R (RX) and U0T (TX) connect to USB-TTL adapter at 115200 baud only while uploading firmware.

Firmware Synchronization Contract #

The main ESP32 reflex firmware exists across three distinct implementations to accommodate different builder skillsets. A strict development contract mandates that any bug fix or threshold modification must be committed across all three files simultaneously:

12 Audited Safety Rules #

Audited in October 2026, these 12 rules prevent firmware lockups, strict-aliasing memory corruption, audio buffer overflows, and dangerous packet leakage:

Rule 01 Bounded Wi-Fi Connection Timeout
WiFi.status() loops are bounded strictly by WIFI_CONNECT_TIMEOUT_MS (15 seconds). Under no circumstances may setup() loop indefinitely waiting for a router: the main loop must begin executing immediately so the offline ultrasonic reflex and tactile button function even if the gateway is completely powered down.
Rule 02 ESP-NOW Callback Version Guard
Supports ESP-IDF 4.x and ESP-IDF 5.x via #if defined(ESP_ARDUINO_VERSION_MAJOR) && ESP_ARDUINO_VERSION_MAJOR >= 3. Handles the API change between const uint8_t *mac and esp_now_recv_info_t without silent compile warnings.
Rule 03 Sender MAC Address Filtering
The main ESP32 invokes isCamera(mac) on every incoming ESP-NOW frame. Frames from unknown or spoofed transmitters are immediately dropped to prevent packet injection or buffer contamination.
Rule 04 Audio URL from /analyse JSON Reply
Audio endpoints are dynamically routed to /audio/<16-hex-chars>. Calling bare GET /audio returns 404; the firmware parses audio_url directly from the JSON analysis response.
Rule 05 HTTP Client Timeouts ≥ 60 Seconds
Standard Arduino HTTPClient defaults to 5 seconds. Because Tier 1 edge inference on complex scenes may require up to 25 seconds and neural TTS up to 20 seconds, timeout is strictly clamped to ≥ 60,000 ms.
Rule 06 Stalled-Frame JPEG Chunk Recovery
If the main board does not receive the next expected 220-byte image slice within FRAME_STALL_TIMEOUT_MS (3 seconds), the partial image buffer is safely purged. This prevents corrupt hybrid images if the camera reboots mid-frame.
Rule 07 Channels Guard in playWavStream
Streamed audio explicitly clamps channel counts: if (channels < 1) channels = 1; if (channels > 2) channels = 2;. A corrupted or malformed header specifying 0 channels will otherwise loop indefinitely and overflow the 512-sample stack buffer.
Rule 08 Safe memcpy for WAV Header Fields
Never cast unaligned byte buffers to uint32_t* pointers, which triggers undefined behavior and unaligned bus faults on the Xtensa processor. Header fields are read exclusively via safe memcpy calls.
Rule 09 DAC Sample Rate Re-Assertion
Before playing any local alert clip, playFile() re-asserts CLIP_SAMPLE_RATE (22,050 Hz) on the I2S clock generator. This ensures network audio streamed at 16,000 Hz or 44,100 Hz never leaves the DAC pitch-distorted for subsequent reflex alarms.
Rule 10 Audited Ultrasonic Stop Threshold
quickRule() asserts: "Obstacle critical. Stop." whenever centre ultrasonic distance drops below 25 cm. The main loop maps any rule containing "Stop" directly to /stop.wav, pre-empting all speech and radio operations.
Rule 11 Disable 802.11 Modem Sleep
Both boards explicitly invoke WiFi.setSleep(false) in initialization. The ESP32's automatic power-saving sleep mode drops short connectionless ESP-NOW packets and introduces unacceptable jitter into the vision stream.
Rule 12 Standardized SCCB Pin Spelling
Camera code strictly uses pin_sccb_sda and pin_sccb_scl (the upstream Espressif standard). Deprecated pin_sscb_* aliases are banished across all builds to guarantee forward compatibility with esp32-camera ≥ v2.0.2.

REST API Specification #

The gateway server exposes an HTTP API adhered to by the web companion, native Android shell, and ESP32 uplink:

Route Endpoint Method Auth Description & Behavior
/api/config GET None Returns gateway configuration: token requirement, maximum frame age threshold (≤30s).
/api/prefs GET / POST POST: Token Retrieves or updates user language, neural voice model, and accessibility text sizing.
/api/tts/voices GET None Returns catalogue of available neural TTS voices for the currently active language.
/api/chat POST Token User prompt + optional camera JPEG payload. Returns assistant answer and generated audio URL. Returns 429 when rate limited.
/api/latest-frame GET Token Returns freshest JPEG camera frame (≤30 s old). Returns HTTP 404 if no fresh frame exists — never a stale placeholder.
/analyse POST None Multipart image upload from ESP32. Runs YOLOv8 edge vision; returns detection summary and speech audio URL.
/audio/<id> GET None Streams rendered reply audio (neural MP3 preferred, espeak WAV fallback).
/sw.js GET None PWA Service Worker served with Service-Worker-Allowed: / header for root scope caching.

Advantages of the Native Shell over Mobile Browsers:

CI & Field Verification (93 Tests) #

Because BlindSight is a personal safety device, it undergoes rigorous automated validation on every commit before release:

Automated Test Suite Breakdown (v3.3 Delivery):

  • Fail-Closed Vision Contracts: Verifies that zero-byte images, corrupt headers, or timeout frames trigger immediate spoken errors rather than placeholder descriptions.
  • Anti-Fake WAV Spectrum Gates: Audio unit tests inspect rendered audio files to ensure valid RIFF headers, correct sample rate assertions (22,050 Hz), and non-empty audio frequency spectrums.
  • Companion Memory Integrity: Rigorous serialization tests ensuring memory writes, updates, and wipes persist across app restarts without data leakage.
  • PWA Shell Accessibility: Headless audit validating WCAG AAA color contrast, ARIA assertive live regions, and touch target minimums.

Honest Limitations & Bench-Pending Items #

In alignment with the principle of failing loudly, BlindSight openly acknowledges its hardware and platform constraints:

  • iOS Wake Word Restriction: Apple iOS Safari does not permit continuous microphone listening in web applications. On iPhone or iPad, the companion requires tapping the primary button and using native iOS keyboard dictation.
  • Ultrasonic Environmental Factors: Soft, sound-absorbing fabrics (e.g., thick wool coats) or acute angles can attenuate 40 kHz ultrasonic echoes. The physical white cane should always accompany the electronic companion.
  • ESP-NOW Wireless Range: ESP32-to-ESP32 camera transmission operates reliably at room-scale distances (~5 to 8 meters line-of-sight).
  • Internet Requirement for Neural Voices: Microsoft neural TTS voices require active internet access on the gateway. In offline mode, the system seamlessly falls back to espeak-ng.
